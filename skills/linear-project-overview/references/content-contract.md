# Project Overview Content Contract

Use this structure, omitting `Non-goals` when no evidenced adjacent ambiguity
exists:

```markdown
## Why
<problem or opportunity and consequence>

## Outcome
<durable target state>

## Scope
<project-level capabilities or responsibilities>

## Non-goals
<plausibly confusing adjacent scope that is excluded>

## Success
<observable project-level end states or meaningful KPIs>
```

Prefer stable responsibilities and boundaries. Name architecture only when
establishing it is itself the outcome. Exclude milestone/issue inventories,
delivery or rollout order, current status, blockers, risks, next steps,
issue-level acceptance, and detailed design. Do not add a `Resources` heading;
native resources own supporting links and documents. Use an inline stable link
only when necessary to understand a statement.
