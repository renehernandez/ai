# Confirmed Agent Provider Messages

## Goal

Require every human-readable GitLab or Linear message written by an agent under
Rene Hernandez's identity to be shown as an exact destination-bound draft and
explicitly confirmed before submission. Every submitted message must disclose
that it was automatically generated and that Rene approved its submission.
[confidence: 0.99 - certain | reason: Rene explicitly accepted this behavior
and its proposed disclosure wording]

## Accepted Decisions

- Cover agent-written GitLab and Linear comments, discussion replies, notes,
  issue comments, and project updates submitted through Rene's identity.
  [confidence: 0.98 - certain | reason: these are the accepted human-readable
  provider-message surfaces]
- Before each submission, show the exact rendered draft, including its
  disclosure, and identify the exact provider destination. Only Rene's explicit
  confirmation of that draft authorizes submission. General implementation,
  delivery, or Finish authority does not satisfy this checkpoint. [confidence:
  0.99 - certain | reason: the accepted behavior requires drafting and
  confirmation before submission]
- Require a new confirmation when either the approved message content or its
  destination changes. [confidence: 0.97 - certain | reason: otherwise the
  submitted message would differ from what Rene reviewed]
- End each covered message with this rendered notice, substituting the active
  harness name: [confidence: 0.99 - certain | reason: Rene accepted the
  automatic-generation and named-approval wording]

  > Automatically generated by `<active harness>`. Approved for submission by Rene Hernandez.

  A Codex-authored message therefore renders `Automatically generated by
  Codex. Approved for submission by Rene Hernandez.`

- Exempt command-only review notes such as `/request_review @nitro` and
  service-generated bot output with a distinct service identity. Preserve the
  existing exclusions for commits and PR/MR descriptions. [confidence: 0.97 -
  certain | reason: Rene accepted these exclusions and these artifacts are not
  human-readable replies submitted as Rene]
- Replace the existing `Co-Authored by: <harness>` comment footer for covered
  GitLab and Linear messages. It identifies a collaborator but does not state
  automatic generation or human approval. [confidence: 0.98 - certain |
  reason: the live referenced note and current rule demonstrate this gap]

## Scope

### In Scope

- Update the canonical provider-message rule in `rules/git-and-review.md`.
- Align Finish so its normal provider follow-through cannot bypass the
  destination-bound draft and confirmation checkpoint for covered messages.
- Align existing GitLab and Linear skills only where they independently own a
  covered human-readable message submission path.
- Add focused regression tests for the rendered notice, draft content,
  destination, confirmation timing, reconfirmation after changes, and accepted
  exemptions.
- Run `writing-skills` against the changed shared agent behavior.

### Out Of Scope

- Changes to Nitro's own bot-authored messages or another service's provider
  identity.
- Disclosure in commits, commit metadata, PR/MR descriptions, issue bodies, or
  other non-message artifacts.
- Confirmation for command-only review notes.
- Changes to provider permissions, authentication, APIs, or UI behavior.
- Retrofitting or editing already-submitted GitLab or Linear messages.
- Merge, deployment, or cleanup.

## Reuse And Deviation Contract

`rules/git-and-review.md` is the canonical owner for human-readable provider
comments and already requires harness attribution. `skills/finish/SKILL.md`
owns provider mutation and follow-through. Existing Linear planning skills
already require previews and approval before Linear writes. Extend those owners
in place rather than adding a message-submission skill or a second approval
system.

The intentional deviation is that covered messages become a human-gated
exception to Finish's ordinary uninterrupted provider follow-through. The new
checkpoint is narrower than general provider-write approval: it binds one exact
human-readable draft and destination to Rene's confirmation and makes that
approval visible in the submitted message. Command-only and distinct-service
messages keep their existing automatic path.

End-to-end proof will exercise a GitLab or Linear reply request through the
normal provider path. The agent must stop with the exact destination and final
rendered draft, then submit only after confirmation and preserve the exact
notice. A changed draft or destination must stop for confirmation again.

## Acceptance Criteria

- An agent cannot submit a covered GitLab or Linear message until Rene confirms
  the exact draft and destination shown in the task.
- General implementation, delivery, Finish, or prior provider-write authority
  never substitutes for message-specific confirmation.
- Covered messages end with the active-harness automatic-generation and exact
  Rene Hernandez approval notice.
- Any content or destination change invalidates the earlier confirmation.
- Command-only review notes and distinct-service bot output remain automatic
  and do not claim Rene approved human-readable prose.
- Commits, PR/MR descriptions, issue bodies, and historical messages remain
  unchanged.
- The canonical rule, Finish behavior, applicable provider skills, and tests
  agree without creating a parallel approval mechanism.

## Risks And Controls

| Risk | Control |
| --- | --- |
| Normal Finish authority bypasses confirmation | Define covered messages as an explicit human checkpoint in the canonical rule and Finish owner. |
| The notice claims approval for changed text | Bind approval to the exact rendered body and invalidate it after any content change. |
| Approval is reused for the wrong record | Include the exact provider destination in the confirmation boundary. |
| Machine commands become unnecessarily interactive | Preserve the narrow command-only exemption and test it. |
| Service bots falsely claim Rene approved their output | Exempt messages produced under a distinct service identity. |
| Similar rules drift across GitLab and Linear skills | Keep the detailed contract canonical and add only narrow routing language to independent submission owners. |
